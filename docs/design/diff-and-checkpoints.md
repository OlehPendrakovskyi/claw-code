# Design: inline diffs, reject and checkpoints

Covers roadmap items **P1-1** (diff view and Accept), **P1-1b** (Reject, v1.x), **P1-1c** (per-change review, v2), **P1-4** (recording checkpoints) and **P1-4b** (Rewind, v1.x). Status: design, not implemented. Back to the [roadmap](../roadmap.md).

## Problem

The agent edits files outside the VS Code process — on the Gateway host or a paired node — and the extension learns about an edit only from the session's toolCall events, after the write has usually already happened. Showing a trustworthy diff, and undoing an edit without destroying the user's own work, therefore depends on what the extension captured *before* the run and on what it can attribute to the agent *after* it.

## Terms

| Term | Meaning |
| --- | --- |
| **Owning root** | The `WorkspaceFolder` a toolCall declares as the root its relative path belongs to |
| **Before-state** | The file contents before the agent touched it |
| **Post-agent baseline** | The contents the agent produced, as recorded by the extension |
| **Wave** | The edits between toolCall lulls within one run; the boundary at which post-agent baselines are recorded (A2). The unit of a checkpoint is the **run**, not the wave |
| **Restore** | Writing a before-state back to disk — used by both Reject and Rewind |

## Threat model

Development rule R59 asks for this before the mechanism. The design defends against:

- **Workspace and repository content.** File contents and names, symlinks and junctions, paths and bytes reported in tool calls: all untrusted (P1–P5, C4a, A1).
- **The agent's output.** Tool-call data is untrusted input even though the Gateway connection itself is authenticated and the user's own (B2, A1, P1a).
- **Other local accounts.** The checkpoint store is owner-only and verified before use (C6c).
- **Publication through ordinary Git use.** No ref-selected push sends a checkpoint (C2a).

Out of scope, stated so the guarantees are not read as wider than they are:

- **A process running as the same user.** It can read or rewrite the store and the repository directly.
- **The user's own Git configuration.** Hooks are disabled for checkpoint commands (C2a), but clean/process filters configured by the user run as they would for any `git add`. A cloned repository cannot set them: `.git/config` is not cloned. A repository whose `.git` directory came from elsewhere is an untrusted workspace, and checkpoints run only in a trusted workspace (VS Code Workspace Trust).
- **An object-ID push the user types deliberately** (C2a).

The checkpoint transport does not use the network: snapshots move only between the user's repository and a local bare store. Programs the user's Git configuration runs during capture and restore are a different matter. A trusted clean filter, such as Git LFS while snapshot capture reads modified files for the index tree (C2/C2a), may reach the network, as it would for any `git add`. A Rewind runs no filter: it writes raw copies (C4b). That traffic belongs to the user's configured tools, under the same trust as above.

## Invariants

These are the binding rules. Each is stated once here; the roadmap and other documents link to this section instead of repeating it.

### Path resolution and containment

- **P1.** A toolCall path is resolved only against the owning root the toolCall **declares**. Never use the deprecated single-root `workspace.rootPath`, and never infer the owner by longest matching prefix: a relative path carries no root, and an inferred owner can be the wrong repository. An ambiguous path is refused with a clear error.
- **P1a. Protocol dependency.** Neither the v4 contract nor the current adapter carries an owning root: `ToolEventData` exposes only `args` / `result`, and the adapter reduces tool events to a display string (`details`, `src/core/gatewayProtocol/v4/events.ts:87-96`, `model.ts:285-296`). So, by P1, every relative tool path is refused today. Until the Gateway declares a root per tool call (an upstream capability, discovered through `hello-ok.features`), P1-1 accepts only **absolute** paths that canonicalise into exactly one open workspace folder, and refuses relative paths. The adapter must also keep tool arguments and results structured rather than as a display string, so file paths and written bytes (A1) can be read.
- **P2.** Containment is checked on **canonical** paths. Canonicalise the root with `realpath`; canonicalise the target with `realpath` when it exists, or canonicalise its nearest existing parent and re-append the remaining segments when it does not. The canonical target must lie inside the canonical root, so neither `..` segments nor symlinks can leave the folder. An escaping path is refused, never guessed.
- **P3.** (Applies development rule R6 to this design's reads.) Canonicalisation is a **pre-operation** check, not a guarantee: a directory can be swapped for a symlink or junction between `realpath` and the open. Reads therefore repeat the check at operation time: open through a handle, `O_NOFOLLOW` on the final component, compare the handle's dev/ino with a fresh `lstat`, and verify the **handle's own path through the operating system** — the fd link on Linux, `F_GETPATH` on macOS, `GetFinalPathNameByHandle` on Windows — against the canonical root before using any byte read. Identity checks alone do not establish containment (an ancestor swapped before both the open and the `lstat` satisfies them), so where no OS-backed handle path is available the read **fails closed**. The current attachment reader (`src/webview/viewMessaging.ts`) does not meet this on Windows, where `handleIsAtPath` returns `true` unconditionally, nor on POSIX systems without a usable fd view; fixing it is **SEC-3**, and diff and restore must not reuse it until then.
- **P4.** Writes must guarantee containment **before** writing, because post-write drift detection can report an escape but cannot undo it. Open the destination through a handle with `O_NOFOLLOW`, verify the handle's location (dev/ino plus the fd link) against the canonical root, and write only through that verified handle — never through a re-opened path string. A dev/ino comparison is **not** a fallback: if an ancestor directory is swapped before the open, the handle and a fresh `lstat` agree with each other while both point outside the root. Writes therefore require a handle-to-path check — the fd link on Linux (`/proc/self/fd`), `F_GETPATH` on macOS, `GetFinalPathNameByHandle` on Windows — and on a platform or filesystem where none is available, the write is refused. Containment is not a staleness question, so user confirmation cannot waive it: where operation-time containment cannot be guaranteed, **every** write to that destination is refused — automatic restore and the explicit force-restore of R2 alike — and the user is told the file cannot be restored safely from the editor.
- **P5.** Creating a file (recreating one the agent deleted) and deleting a file (removing one the agent created) cannot use P4, because there is no destination handle to open or verify. Both must be done **relative to a verified parent-directory handle**: open the parent directory with `O_DIRECTORY | O_NOFOLLOW`, verify that handle against the canonical root as in P4, then create with `openat(dirfd, name, O_CREAT | O_EXCL | O_NOFOLLOW)` or delete with `unlinkat(dirfd, name)` (on Windows, the equivalent handle-relative create and delete-on-close through a handle opened without following reparse points). Node's `fs` module exposes no directory-handle-relative create or unlink, so until a safe primitive is available (for example a small native helper), these two cases are **unavailable** for both automatic and forced restore. Rewind lists such paths as not restored, for the user to handle by hand.

### Before-state

- **B1.** Admissible sources of the before-state, in order: (a) a snapshot captured before the run; (b) an acknowledged pre-write protocol in which the client applies the edit itself (v2, below); (c) git HEAD or a stash, **only** if it was captured before the run or the file's cleanliness was verified beforehand.
- **B2.** The toolCall *start* event is not a pre-write barrier — the Gateway can emit it and finish the write before the extension receives it — so a pre-read triggered by it is not a before-state.
- **B3.** When no admissible source exists, the diff reports the before-state as **unavailable**. A late HEAD diff is never presented as the agent's diff: a file with uncommitted user edits would attribute those edits to the agent.

### Post-agent baseline

- **A1.** The baseline is valid only when it is **attributable to the agent**: the bytes or a hash observed as the toolCall result, or change tracking established before the run began. Reading the file when the toolCall completes is not enough on its own — the write and the event are asynchronous, so a user edit in the gap would be recorded as agent output.
- **A2.** The baseline is recorded once, at the toolCall completion / wave-close boundary, and never refreshed. Reading it later (for example when the diff or rewind UI opens) silently adopts any user edit made in between.
- **A3.** If the baseline cannot be attributed, the automatic restore is refused as ambiguous; offer a three-way conflict flow or an explicit force-restore instead.

### Restore (Reject and Rewind)

- **R1.** `git checkout -- <file>` is not a Reject: it restores HEAD and destroys uncommitted edits that existed before the agent started. HEAD is used only when the file's cleanliness was verified beforehand (B1c).
- **R2.** A restore is **conditional**: it proceeds only if the current on-disk contents still equal the post-agent baseline. Otherwise refuse, tell the user the file changed, and offer an explicit force-restore. Force bypasses only this content check: a forced write still satisfies P1–P4 or is refused.
- **R3.** The R2 comparison is a **staleness check, not a compare-and-swap** — an edit landing between the compare and the write is still overwritten — and the UI must not describe the restore as safe. None of these close that window: a temp-file rename (atomic replacement, but not conditioned on the destination), re-comparing just before the replace, writing under a content-addressed key (does not touch the destination), or `RENAME_NOREPLACE` (fails whenever the destination exists, so it cannot replace a file at all).
- **R4.** An **automatic** restore requires a true compare-and-swap on the destination, conditioned on its exact version or generation (a versioned update, a generation-conditional write, or a platform compare-exchange). No filesystem primitive on this project's targets qualifies today, so automatic restore stays disabled and Reject/Rewind ship as the explicit conflict/force flow. See *Open questions*.

### Checkpoints

- **C1.** Take the snapshot **before every run that can edit files** — any run whose mode or agent permits writes — not when the first file-effect toolCall arrives: by then the write has already happened (B2). A run that ends without file effects simply discards its snapshot. The checkpoint unit is the **run**: Rewind returns the run's touched paths to their pre-run state, and rewinding to a point between two waves of the same run is not offered, because only the pre-run snapshot exists. Wave boundaries are used only to record the post-agent baselines and index entries the guards compare against.
- **C2.** Git snapshot: `git stash create` (it does not touch the index), with the SHA stored in the session's checkpoint registry. On a clean tree it prints nothing and exits 0, so the checkpoint always records an explicit baseline instead: the HEAD commit, or the index tree from `git write-tree` when the index differs from HEAD. With an unborn HEAD (fresh `git init`) `git stash create` cannot run and `git write-tree` records only the **index** (the empty tree when nothing is staged). A file staged and then edited again before the first commit has worktree bytes that neither captures, so in an unborn repository the checkpoint additionally shadow-copies (as in C6) every tracked path whose worktree contents differ from the index. With that addition every git repository has a complete baseline.
- **C2a. Snapshots are kept reachable, outside the user's refs.** A `git stash create` commit and a `git write-tree` tree are dangling objects: storing only their SHA does not stop `git gc` from pruning them before a Rewind needs them. They are kept alive in an **extension-owned bare repository**, one per user repository, inside the owner-only checkpoint store of C6c — never as refs in the user's repository. When a snapshot is taken, the extension copies into the store **only the snapshot's index tree and its blobs**: `<stash>^2^{tree}` when `git stash create` produced a stash, otherwise the C2 baseline, which is `HEAD^{tree}` on a clean tree or the `write-tree` result when the index differs from HEAD (including an unborn HEAD). Working-tree bytes are kept raw by C4b, not as a Git tree. To transfer just that tree, it is wrapped in a **parentless commit** (`git commit-tree <tree>` with no `-p`, run with a fixed extension identity through `GIT_AUTHOR_*`/`GIT_COMMITTER_*`). The commit has no history, so pushing it sends only that tree and its blobs, never the repository's ancestry, and a commit is an ordinary push target in any namespace. `commit-tree` runs no hooks. A Rewind takes the index tree back as `<commit>^{tree}`. This is kept under `refs/checkpoints/<session>/<run>/index`, where `<session>` and `<run>` are the lowercase hex SHA-256 of the Gateway-supplied ids, validated with `git check-ref-format`. A Rewind fetches them back into the user's object database before restoring with `git fetch --no-write-fetch-head`, so the fetch names nothing: no ref, and no `FETCH_HEAD` that a configured push refspec could resolve. **No hooks run on either side of any transfer.** The store is created from an empty template (`git init --bare --template=<empty dir>`) with `core.hooksPath` set to an extension-owned empty directory, so neither an inherited `init.templateDir` nor anything else can give it `pre-receive` or `update` hooks. Every checkpoint command run against the user's repository passes `-c core.hooksPath=<that empty directory>`, which covers `pre-push` and any other client hook, and a push also passes `--no-verify`. Other configured programs are controlled per path, rather than covered by a blanket claim:

- `core.fsmonitor` is turned off for every checkpoint command (`-c core.fsmonitor=false`).
- Automatic maintenance is off: `-c maintenance.auto=false -c gc.auto=0` on the user's repository, `--no-auto-maintenance` on fetches, and `receive.autogc=false` and `gc.auto=0` in the store's own config.
- The store's retention clean-up is the extension's own explicit `git gc` on the store, whose config the extension owns (no `gc.recentObjectsHook`, no hooks).
- Clean/process filters are not disabled. `git stash create` reads modified files exactly as `git add` would, so the snapshot holds what the repository would commit. Those filters come from the user's own Git configuration, which the threat model trusts, and checkpoints run only in a trusted workspace. The bytes and file count a snapshot adds to the store count against the C6a limits; a snapshot that would exceed them, or whose transfer fails, is not recorded, and the run follows C6b (no checkpoint, the user told before the run starts). Because nothing in the user's repository references these objects, no push that selects what to send from refs — an ordinary branch push, `--mirror`, or a configured refspec, now or after a later configuration change — includes a checkpoint. The guarantee stops there. The snapshot objects stay in the user's object database as unreferenced objects until `git gc` prunes them, so a user who explicitly pushes an object ID (`git push origin <sha>:refs/tags/x`; `refs/heads/` accepts only commits) can still publish one. That needs a deliberate, ID-specific command and is documented as such, not prevented. Store refs follow C6a retention, are deleted with their session, and are swept on activation when the registry no longer lists them; removing the store directory removes every checkpoint. A Rewind whose store ref or object is missing is refused as "checkpoint unavailable", never approximated.
- **C3.** Preserve the pre-run **index tree** and restore index and worktree separately. `git checkout <stash> -- .` updates both and turns pre-existing unstaged edits into staged ones.
- **C4.** Rewind touches only the agent's paths, never the whole tree, and restores the **worktree and the index separately** per C3 — never with `git checkout <snapshot> -- <paths>`, which writes one version into both and collapses a path's distinct staged and unstaged pre-run versions. For each path: (a) the worktree bytes come from the raw copy taken at snapshot time (C4b) and are written through the verified handle of P4, after the R2 check against the per-path post-wave contents recorded at wave close (A1–A3); (b) the index entry comes from the recorded pre-run index tree (the index tree C2a keeps in the store, taken from the stash's index parent or from the `git write-tree` / HEAD baseline of C2) via `git restore --staged --source=<index tree> -- ':(literal)<path>'`, which removes the entry when the path was not in that tree. The index has **its own guard**, independent of the worktree's: at wave close the checkpoint also records each touched path's post-wave index entry (mode, blob and stage, as `git ls-files --stage -- ':(literal)<path>'` reports it), and the index is restored only if the current entry still equals that record. If the user has since run `git add`, `git reset` or anything else that changed the entry, or no post-wave entry was recorded, the index is left untouched and the conflict is reported — even when the worktree restore went ahead. A path refused under R2 is left untouched in both the worktree and the index.
- **C4a. Literal paths.** `--` only ends option parsing; git still reads what follows as a pathspec, so a file name containing `*`, `?`, `[` or a leading `:` would match more than the one file. Every git command that takes an agent-touched path — restore, guard queries, snapshot reads, `git diff` requests — passes it as a literal pathspec: `:(literal)<path>` per argument, or a NUL-delimited `--pathspec-from-file=<file> --pathspec-file-nul` list with `GIT_LITERAL_PATHSPECS=1` set. Blob reads use `git cat-file` with the object ID from the recorded tree, not a path lookup. A command that cannot take a literal pathspec is not used.
- **C4b. Working-tree bytes come only from raw copies.** A Rewind never rebuilds working-tree bytes from Git blobs. Conversion depends on clean/smudge filters, `core.autocrlf`, `.gitattributes` and other settings that may have changed since the snapshot (the agent can edit `.gitattributes` itself), and Git can call a file clean while its raw bytes differ from what checkout would write. So the C1 snapshot copies the **raw bytes and the file mode (the executable bit) of every tracked file** in the working tree, as well as the untracked files of C5, into the content-addressed store of C6a. A Rewind writes exactly those bytes and sets that mode through the verified handle of P4 (`fchmod`), under the same R2 guard. A post-wave baseline records the mode too, so a mode change made by the user after the run is a conflict like a content change. On a filesystem that has no executable bit, the mode is not restored, and the path is reported as restored without its mode. **Symlinks are not covered.** Capture records each tracked symlink's path and target text (read with `lstat`/`readlink`, never followed), so a Rewind can detect that one was changed or replaced. But it cannot recreate it: that is a create/delete, which P5 leaves unavailable. Such paths are listed as not restored, like the other C6b exclusions, and their bytes are never written through the link. Unchanged files are stored once across checkpoints, so the cost is one full copy and then only changed files, within the C6a limits and with the C6b fallback. The Git trees of C2/C2a serve only the index: C4 (b) restores index entries in repository form, as the index holds them.
- **C5.** `git stash create` does not cover untracked files, and a checkout does not remove files created after the snapshot. The checkpoint therefore also records the set of untracked / new / deleted paths **and** the contents plus mode and mtime of pre-run untracked files, tracks the files the run creates, and restores them under the same R2 guard. Recreating deleted files and removing created ones follows P5.
- **C6.** Non-git folders use shadow copies under `~/.openclaw/vscode-checkpoints/`.
- **C6a. Resource bounds.** Every raw copy (C4b working-tree files, C2 unborn repositories, C5 untracked files, C6 non-git folders) goes into a content-addressed store, so an unchanged file is stored once however many checkpoints reference it, and each checkpoint copies only files whose size, mtime or hash changed since the previous one. The store is bounded by configurable limits — total bytes and file count per checkpoint, a per-file size ceiling, and exclusions (`.gitignore` rules where present, plus build and dependency directories such as `node_modules`, `dist`, `out`) — and by retention: the last N checkpoints per session and a maximum age, with unreferenced blobs garbage-collected when a checkpoint is dropped or its session is closed.
- **C6c. Confidentiality.** Checkpoint blobs hold source files and possibly secrets, so the store's root directory is created **owner-only** (mode `0700`, or an ACL granting only the current user on Windows) and every blob owner-only (`0600`), set explicitly rather than left to the umask; before each use the root is checked to be a real directory (not a symlink or junction), owned by the current user, and not accessible to other accounts, and a root that fails the check is refused rather than repaired in place.
- **C6b. Failure behaviour.** If a checkpoint would exceed a limit, or the disk lacks space, no partial checkpoint is recorded. The run still starts, but the UI marks it as having **no checkpoint** — Rewind is unavailable for it and the user is told why before the run begins, with the option to cancel. An excluded or oversized file is listed as not covered by the checkpoint and is never silently restored or deleted by a rewind.
- **C7.** Repositories on a NAS (see the deployment topologies in the [roadmap](../roadmap.md#5-deployment-topologies)) are checkpointed by the agent at the extension's request, or via node exec when a paired node exists (preferred) — v2.

## Mechanism

0. **Pre-run snapshot.** When a run that can edit files starts, take the checkpoint per C1–C6b before sending the prompt.
1. **Interception.** The event reducer recognises a toolCall with a file effect (the `write` / `edit` / `apply_patch` class). Concrete tool names come from discovery and the agent runtime; the mapping lives in the protocol contract layer.
2. **Location.** Resolve per P1–P4. A file on a NAS that the window cannot reach goes to step 5.
3. **Rendering.** `vscode.diff` between two read-only `openclawOriginal:` documents: the left side holds the before-state (B1–B3) and the right side holds the **captured post-agent baseline** (A1–A2) — never the live working file, which would attribute later user edits to the agent. When no attributable baseline exists, the diff is not shown as the agent's change (A3). If the live file has since diverged from the baseline, the diff view is marked **stale** and offers a separate comparison of the baseline against the current file, so the user's later edits are shown as theirs.
4. **Decision.** Accept marks the edit reviewed. Reject restores per R1–R4.
5. **Unobserved edits.** When the file is not reachable through the filesystem, show a textual diff in the chat (from the toolCall details or a `git diff` requested from the agent) with **Accept only**. The extension cannot check R2 on a file it cannot read, so it offers no one-click Reject. A Reject appears only when a paired node or Gateway API can perform the guarded restore itself — the R2 comparison against the recorded baseline and the write, on the host that owns the file. Without one, the user can still ask the agent to revert the file, but only through the explicit force flow, after a warning that any edits made since the tool call will be lost.
6. **Rewind.** A rewind button on a message restores the checkpoint (C1–C7). Forking the conversation (a new Gateway session with the history copied) is v2.

### v2 extensions

- **Pre-apply.** In Manual mode the agent returns the proposed content in the toolCall details and the extension applies it itself — local repos only. This is source (b) of B1.
- **Per-change review.** Accept/Reject buttons under each change in the diff (TextDocumentContentProvider plus decorations, up to 100 changes), and `openclaw.acceptChangeAtCursor` / `openclaw.rejectChangeAtCursor` driven by cursor position.

| Stage | Ships |

## Open questions

1. **Owning root per tool call (P1a).** Request it upstream; until then only absolute paths are supported.
2. **Compare-and-swap (R4).** Is there any conditional-write primitive on Linux, macOS and Windows that can be conditioned on the destination's version? Until there is, automatic restore stays off.
3. **Agent-attributable bytes (A1).** Does the Gateway's toolCall result carry the written bytes or a hash? If not, request it upstream — without it every baseline is ambiguous.
4. **Checkpoint limits.** The default values for C6a (bytes, file count, per-file ceiling, retention N and age).
5. **File-effect tool names.** Which tool names and argument shapes the contract layer must map, per agent runtime.
